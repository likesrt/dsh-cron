# dsh-cron

[English](README.en.md)

DSH 的定时任务插件：到点跑一条命令，或者把一句 prompt 交给模型跑一轮；结果按需推回聊天。侧边栏一个入口，页面嵌在主区域里，任务数据跟着工作区走。装上后默认接管内置的「自动化任务」。

## 安装

**强依赖 [dsh-im](https://github.com/xmanrui/dsh-im)。** 推送 IM 靠它——微信、企微、飞书、钉钉、QQ、Telegram、WhatsApp、Slack、Discord、Matrix 的通道和目标都由 dsh-im 提供；没装 dsh-im，推送里就只剩静默、回原会话、会话日志三种出口。

先装 dsh-im：

```bash
dsh plugin --profile web add @xmanrui/dsh-im        # profile 名字换成你自己的，这套 Web 界面是 web
```

装完在「设置 → IM机器人」里配好机器人、保存至少一个投递目标——本插件的 IM 出口只能选那里保存过的目标，不认裸 id。

再装本插件：

```bash
dsh plugin --profile web add github:likesrt/dsh-cron        # 仓库 https://github.com/likesrt/dsh-cron
```

`--profile` 是必填的，写你的 profile 名（这套 Web 界面是 `web`）。

不想进终端：「插件」页 → 安装插件 → 粘贴 `github:likesrt/dsh-cron` → 安装。

命令行那条只是把包装进 profile，装完还要在「插件」页把 `dsh-cron` 打开；插件页里直接安装则一步到位。之后刷新浏览器，左侧边栏出现「定时任务」。纯 JS，没有构建步骤，装完即用。

- 更新：`dsh plugin --profile web update dsh-cron`。同一条 `add` 命令不会重新解析 git，pnpm 会认为锁文件已是最新；`update` 才会重新拉 HEAD，拉完重启宿主或重载插件生效。
- 卸载：`dsh plugin --profile web remove dsh-cron`。
- 需要能访问 github.com；内网走代理的话先配好 git 的代理。
- 装上默认关掉内置的「自动化任务」，想两套并存就关掉配置里那个开关。

## 和内置「自动化任务」的区别

| | 内置 自动化任务 | dsh-cron |
|---|---|---|
| 本质 | 到点把一句话送进会话，模型跑一轮 | 作业：跑脚本，或把 prompt 交给模型 |
| 跑命令 | — | 有，直接执行，不经模型 |
| 结果去哪 | 只能进会话 | 静默 / 回原会话 / IM 目标 / 会话日志 |
| 推不推 | 每轮都投递 | 由每轮自己决定：脚本 stdout 空则静默，模型回 `[silent]` 则静默 |
| 执行位置 | 已有会话、首次创建后沿用、每次新建 | 同左 |
| 调度 | at / after / every / daily / weekly / cron / rrule | 仅一次 / 每月 / 每周 / 每天 / 每小时 / 每 N 天·小时·分钟·秒 / cron（5 或 6 段） |
| 每条任务的 Agent、模型、权限 | Agent 预置在建会话时定 | 每条任务单独指定，跑前切到该会话 |
| 失败重试 / 单次超时 | — | 0..5 次退避重试；超时连子进程组一起杀 |
| 次数上限 | — | 有，跑够就停 |
| 运行历史 | 投递记录（默认留 30 天 / 200 条） | 每次运行的输出与错误，可跳回那次会话；保留天数与条数可配 |
| 删除任务 | 只删任务 | 任务和它建出来的会话一起收走（会话一并归档） |
| 连续失败 | — | 故障记录与确认 |
| 立即执行 | 有 | 有 |
| 数据 | 宿主级 `$DSH_HOME/storages/schedule.json` | 按工作区 `<workspace>/dsh-cron/` |
| 模型工具 | 4 个：list / view / create / edit | 12 个：另有 run / runs / targets / notepad / incidents / health |
| 页面 | 内置任务页 | 侧边栏内嵌页，右侧抽屉编辑，另有故障页 |

## 两种模式

| 模式 | 做什么 | 推不推 |
|---|---|---|
| 脚本模式 | 直接跑一条命令，不经过模型 | stdout 有内容就推，空着就静默 |
| 智能模式 | 把 prompt 交给模型跑一轮 | 配了渠道时，模型整段只回 `[silent]` 就不推这一轮 |

两种模式都留运行记录，`deliveryReason` 写清这一轮为什么推、为什么不推。

## 调度

界面全是选择器，不用手写表达式：仅一次 / 每月 / 每周 / 每天 / 每小时 / 每 N 天 / 每 N 小时 / 每 N 分钟 / 每 N 秒 / 自定义 cron。单位跟着控件走，选择器下面直接给下次执行时间。

- 月 / 周 / 日 / 时与自定义 cron 按日历算，时区取配置里的 `timeZone`，夏令时跳变和回拨都处理了。
- `每 N …` 是等间隔语义，按绝对时间推进（不会有 `*/45` 那种 45/15 交替）。
- 秒级最小 5 秒。
- 只挂一个定时器：按所有启用任务里最早的到期时间 `setTimeout` 一次，醒了重算；没有启用任务就不挂，进程不空转，另有五分钟兜底巡检吸收系统时钟跳变。
- 仅一次：选日期加时间，跑完自动停；过去的时间不补跑。

## 推送

一个任务只有一个出口，成功失败共用：

| 出口 | 结果去哪 |
|---|---|
| 静默 | 只留历史，不发消息 |
| 回原会话 | 回到发起这条任务的地方；聊天里建的回到那个聊天，Web 会话里建的写回该会话日志 |
| IM | 推到 dsh-im 的某个已保存目标 |
| 会话日志 | 追加到指定会话的日志，不驱动模型 |

**不写推送，就是从哪儿建的回到哪儿。** 在企微 / QQ 里让模型建任务，它拿不到 `botId`、`targetId`，也不需要：任务记住「是这个聊天」，跑完发回去，聊天里 `/new` 换了会话也照样认得。在 Web 端会话里建的，写回那个会话的日志。

写会话日志要求那个会话当前开着，关掉之后再跑会记一条「那个会话没开着，写不进去」，不假装成功。想要彻底留痕就把「执行位置」设成那个会话。

### 在聊天里指定目标

`botId` 是机器人，`targetId` 是你在「设置 → IM机器人 → 目标」里保存的别名。聊天里建模模型可以只写目标名，或什么都不写：

```json
{ "kind": "im", "target": "yuyan" }              // 目标名或 targetId
{ "kind": "im", "target": "单聊", "bot": "qq" }    // 多个同名目标时用渠道分开
{ "kind": "im" }                                  // 只保存了一个目标时，什么都不填也用它
{ "kind": "origin" }                              // 回发起任务的地方
```

解析发生在每次投递前，之后改了目标路由也不用动任务；对不上或对上多个时，`deliveryReason` 会把候选项列出来。模型建任务前会调 `cron_targets` 看有哪些目标，不靠猜。

## 执行位置与权限

| 执行位置 | 行为 |
|---|---|
| 新建会话并复用 | 首次运行建一个，之后沿用 |
| 每次新建会话 | 每次运行各建一个 |
| 关联已有会话 | 选一个该工作区下的现有会话，直接在里面跑 |

脚本任务不经过会话，没有这一项。

任务建出来的会话归任务所有，删任务时一并归档：会话从各处列表里消失，需要时还能从归档里捞回来，「关联已有会话」那种动的是你自己的会话，删任务不碰它。

权限来源不同：脚本模式用跑 dsh 的用户的权限（不经沙箱、不走审批）；智能模式用会话自己的权限预设（`read-only` / `workspace-write` / `danger-full-access` / `auto`，`auto` 适合半夜没人应答的任务）。

「运行 Agent」「运行模型」只在智能模式出现，跑之前切到该会话上，不选就跟随宿主默认。

## 失败重试与超时

每条任务可单独设失败重试（0..5 次，退避 5s × 第几次）和单次超时（秒）。重试期间只按最后一次结论推送，中间那几次不外发；超时不重试。

## 面板

左侧边栏点「定时任务」，在主区域内嵌打开。

- 顶部：标题、新建（下拉可直接选脚本模式或智能模式）、故障入口。
- 页签：已开启 / 已暂停 / 已结束 / 全部，带条数；下面是搜索。
- 每行：下次执行、任务与周期、工作区、上次结果，右侧是立即运行、会话、暂停、编辑、历史、删除。
- 编辑用右侧抽屉，分「执行内容 / 执行 / 运行时间 / 失败处理 / 结果」五段。
- 删除要二次确认，确认框里带着这条任务的周期和工作区；任务建过会话的，会说明会话一并归档。
- 操作结果统一用浮层提示。

## 工具

| 工具 | 作用 |
|---|---|
| `cron_create` | 新建任务：名称、周期、模式、脚本或 prompt、工作区、Agent、模型、权限、执行位置、推送、次数上限、重试、超时 |
| `cron_list` | 列出所有任务（含已停止），按下次执行排序 |
| `cron_view` | 一条任务的完整配置与状态 |
| `cron_edit` | 改一条任务（字段同上，另可启停） |
| `cron_run` | 立即运行一次，不影响调度节奏 |
| `cron_remove` | 删除一条任务 |
| `cron_runs` | 执行历史：状态、耗时、输出、错误 |
| `cron_targets` | 列出 dsh-im 已保存的投递目标 |
| `cron_notepad` | 任务的跨运行记事本（KV） |
| `cron_incidents` / `cron_ack` | 长期失败事件：列表与确认 |
| `cron_health` | 体检：缺脚本、缺 prompt、调度写坏、推送 id 写残 |

## 数据

每个任务属于一个工作区，数据落在该工作区下：

```
<workspace>/dsh-cron/
  tasks.json        任务
  runs.jsonl        执行历史（超过保留天数或条数时自动清理）
  incidents.json    故障记录
  .tick.lock        跨进程 tick 锁
```

工作区登记表在 `$DSH_HOME/dsh-cron/workspaces.json`；服务启动时合并所有已登记工作区的任务。

## 配置

「插件」页点进 `dsh-cron`，正文下面就是配置区，只放你能决定的事：时区、单次超时（秒）、并发上限、历史保留（天 / 条）、是否停用内置的自动化任务。都是可热改的，改完下一次运行起的记录就按新规则留。

```yaml
- id: dsh-cron
  config:
    timeZone: Asia/Shanghai
    timeLimitMs: 180000    # 单次执行硬上限，连子进程组一起杀
    maxConcurrent: 3
    historyDays: 30        # 单条运行记录留几天
    historyRecords: 200    # 每个任务留多少条
    disableBuiltinSchedule: true
    devReload: true        # 重新挂载插件时重载实现体
```

「停用内置的自动化任务」不是记个值：保存时面板会打 `/dsh-cron/api/builtin`，由 `pluginManager` 把官方那几行写进 profile 补丁并即时重载，重启后依然是这个状态。

## 与内置自动化任务的关系

包自带的 `cordis.patch.yml` 关掉内置的 `schedule`、`tool-schedule`、`ui-schedule` 三行，避免两套并存。想保留内置那套不用改文件：把配置里那个开关关掉即可。`tool-schedule` 挂在别的分组里，`pluginManager` 的清单不列它，所以开关能控制的是官方页面和它的调度服务。

## 开发

```
lib/
  index.js        插件入口（apply + Config 壳）
  app.js          组装：服务、工具、路由
  core/           纯逻辑：任务模型、调度表达式、故障记录
  runtime/        干活：调度循环、脚本执行、模型调度、投递
  data/           落盘：按工作区存任务、跨进程锁
  api/            对外：面板接口、模型工具、内置开关
client.js         面板（单文件，模块加载器直接加载）
test/             node:test，不起浏览器
```

- 改 `client.js`：刷新页面即可。
- 改 `lib/`：插件管理里关掉再打开 `dsh-cron`，`devReload` 会重新 import 实现体；改 `lib/index.js` 这个壳才需要重启 host。

```bash
node --test test/*.test.js        # 全部
node test/smoke-server.mjs 13999  # 起一个真服务点接口，用临时工作区，不碰真实数据
```
